# ProtoVid analytics contract

Use the `/api/stats` 30-day funnel and `scripts/db-revenue-query.sql` for
product decisions. Both use the same actor and paywall rules below.

## Identity and counting

Plugin events must include the stable `metadata.anonymousId` generated by the
plugin. It is the canonical actor key. When an email is eventually captured,
the stats query maps that email back to its most recent anonymous ID so Stripe
and web events join the same person instead of creating a second funnel actor.
Server-only events without that mapping fall back to a normalized email.

Always use the `*Users` metrics for funnel conversion. `firstOpenEvents` is a
diagnostic event count only: `first_open` is emitted on every plugin load and
is not a new-user denominator.

`exportStartedAttempts`, `exportCompletedAttempts`, and
`transcodeCompletedAttempts` are the reconciliable metrics for new data. They
count distinct `metadata.export_id` values; older events without an
`export_id` remain visible through the legacy user/event metrics but cannot be
joined across the plugin and backend.

The historical 30-day discrepancy between frontend export starts and backend
transcodes is instrumentation drift, not confirmed render fan-out: the 168
`video_export_completed` rows were written with `plugin_version = 'backend'`
and no export ID, while the 47 frontend `export_started` rows came from plugin
versions 1.3.3–1.3.5. New exports propagate one export ID through all retries
and backend transcode operations.

## Canonical product funnel

`session_opened` → `prototype_detected` → `prototype_path_selected` (when a
path is chosen) → `export_started` → `export_completed` →
`download_clicked` → `upgrade_clicked` → `checkout_created` →
`checkout_opened` → `payment_confirmed`

The no-flow activation path also records `setup_guide_opened` when a user opens
the example/setup guide from the empty state. Use it to compare setup-guide
engagement with subsequent `prototype_detected` and `export_completed` users.

For branching prototypes, `prototype_path_auto_selected` means ProtoVid chose
the recommended valid route so the user can export immediately; an explicit
`prototype_path_selected` still records a user-chosen alternate route.

- `export_completed` is only for a successfully produced, valid MP4. Failed
  attempts use `export_failed`; `export` remains a legacy compatibility event.
- `checkout_created` is server-side and means Stripe returned a Checkout
  Session. It is the correct denominator for checkout-open and payment rates.
- `payment_confirmed` is written by the Stripe webhook and is the canonical
  paid-conversion event. A client redirect alone is not proof of payment.

## Monetization surfaces

These are deliberately separate:

| Event/metric | Meaning |
| --- | --- |
| `upsell_card_viewed` / `upsellCardViewedUsers` | A non-blocking upgrade card was shown. |
| `quotaPaywallViewedUsers` | Export was blocked by a free-limit or expired-trial wall. |
| `legacyAmbiguousPaywallViewedUsers` | Historical `paywall_viewed` with no usable reason or trigger; do not use for conversion decisions. |
| `rawPaywallViewedUsers` | All raw `paywall_viewed` events, provided for reconciliation only. |

For a quota wall, emit `paywall_viewed` with one of:

- `reason: free_limit_hit`, `free_limit`, or `trial_expired`; or
- `trigger: free_limit_ui_shown`, `free_limit_reached`, or `trial_expired`.

For an upsell, emit `upsell_card_viewed`; do not reuse `paywall_viewed`.
`paywallViewedUsers` remains an API compatibility alias for the correctly
classified quota metric.

## Project Pass primary experiment (shipped)

`project_pass_primary_v1` has been shipped: whenever the $4 Project Pass is
available, every user sees it as the primary post-export offer, with the $5/mo
Pro plan as secondary. The `pro_first` arm remains as an automatic fallback
for environments where the Project Pass price ID is not configured.

Historical variants in the experiment:

- `pro_first`: $5/month Pro is primary; the $4 Project Pass is secondary.
- `project_pass_first`: the $4 Project Pass is primary; Pro is secondary.

Every `pricing_variant_assigned`, `upsell_card_viewed`, `upgrade_clicked`,
`checkout_created`, and `payment_confirmed` event still carries
`offer_experiment_id`, `offer_experiment_variant`, and `primary_offer`.
Stripe Checkout metadata preserves the assignment across the anonymous-to-email
identity transition.

Use `offerExperiment30d` in `/api/stats` to keep tracking the shipped variant's
absolute performance. New assignments will now all resolve to
`project_pass_first`; the residual `pro_first` counts represent users who
were assigned before the ship or who hit the fallback path.

## Billing lifecycle events

| Event | Source of truth |
| --- | --- |
| `checkout_created` | Checkout API successfully created a Stripe Session. |
| `checkout_blocked_active_entitlement` | Checkout API intentionally prevented a duplicate active paid entitlement. |
| `checkout_opened` | Plugin handed the customer a Stripe Checkout URL. |
| `checkout_completed`, `payment_confirmed` | Stripe webhook completed and paid the checkout. |
| `billing_management_link_requested` | Customer requested a signed billing-management link by email. |
| `billing_management_token_issued` | A completed recurring purchase received a scoped billing-management link. |
| `subscription_cancellation_scheduled` | Stripe accepted cancellation at period end. |

The share loop is measured as `share_link_created` → `review_room_opened` →
`review_comment_created` or `review_status_updated`. `review_feedback_positive`
and `review_feedback_not_yet` measure the post-export review prompt, while
`viral_growth_action` records a completed community/referral action.

The invite experiment is measured as:

`review_invite_experiment_exposed` → `review_invite_panel_shown` or the control
share surface → `review_invite_link_copied` / `review_invite_email_clicked` /
`review_invite_native_share_completed` → `review_room_opened` →
`review_comment_created` or `review_status_updated`.

The predefined success metric is the treatment variant's review-room-open rate
among exposed users compared with control. `shareInviteExperiment30d` in
`/api/stats` contains exposure, distribution, room-open, and review-action
counts for both cohorts. The retention proxy is the review-action rate after a
room opens plus repeat `review_room_opened` event counts by cohort; the
downstream revenue metric is Pro conversion among exposed creators.


Attach `plan`, `pricing_variant`/`pricingVariant`, `price_label`/`priceLabel`,
and `amount_cents`/`amountCents` wherever that context is available. Attach a
`source` to all upgrade and billing events.

## Revenue reporting

Stripe Charge `amount` is gross paid revenue even after a refund. Net revenue
is:

`sum(paid charge amount) − sum(paid charge amount_refunded)`

This handles both full and partial refunds exactly once. Use the revenue API
or audit script output; do not derive revenue by excluding refunded charges
and then subtracting them again.
